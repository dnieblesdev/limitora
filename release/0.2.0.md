# Limitora 0.2.0 Release Preparation Dossier

**Status:** release preparation only. `0.2.0` is not published to PyPI, and a
GitHub Release does not yet exist. This dossier records the protected release
controls and the handoff required before an annotated tag is pushed.

## Release Scope

- OpenCode Go uses the supported API endpoint through the opt-in provider
  contract and CLI boundary.
- The typed public API, deterministic output projections, provider-aware
  `limitora status` CLI, and Codex JSONL adapter remain covered by tests.
- The base package has no mandatory runtime dependencies; the `opencode-go`
  extra supplies HTTPX.
- Python 3.10-3.14 compatibility and installed wheel/sdist smokes remain
  required.

### Known Limits

- `0.2.0` is not published to PyPI, and its GitHub Release does not yet exist.
- CI has no real provider credentials or provider access; provider smokes are
  hermetic and network-blocked.
- Issue #18 remains open and independent: its protocol/E2E work is not
  resolved by `0.2.0`.
- `python -m limitora` is not a supported entry point.
- No claim is made beyond the evidence recorded after protected validation.

## Release Identity

| Item | Required value |
| --- | --- |
| Version | `0.2.0` |
| Tag | `v0.2.0` |
| Workflow | `.github/workflows/protected-release.yml` |
| Ledger schema | `1` |
| Trusted branch | `origin/main` |
| Candidate relationship | Candidate is a strict ancestor of trusted main |

The ledger is intentionally a preparation anchor, not a claim that the
preparation tree is taggable as `0.2.0`. After this release-preparation commit
is reviewed and merged, the ledger must be rewritten on the later trusted-main
commit with the exact reviewed candidate SHA and version. The candidate tree
must contain `version = "0.2.0"`; the later trusted main commit contains the
ledger authorizing that earlier candidate.

This two-commit boundary is required because a candidate cannot contain a
ledger that authorizes the candidate's own SHA without self-reference.

## Candidate and Ledger Strategy

The existing workflow is intentionally unchanged. It avoids the
self-referential candidate SHA as follows:

1. On a tag push, fetch `origin/main` and resolve `trusted_main_sha` from
   `origin/main^{commit}`.
2. Peel the annotated `v0.2.0` tag to `candidate_sha`; require the tag to be
   annotated, the candidate to be a commit, and the candidate to differ from
   `trusted_main_sha`.
3. Require the candidate to be an ancestor of `trusted_main_sha`, then check
   out the candidate itself for version inspection, build, and validation.
4. Read the ledger from trusted main with
   `git show "$trusted_main_sha:release/ledger.json"`, not from the tagged
   tree.
5. Require schema 1, version `0.2.0`, and the ledger source SHA to equal the
   peeled candidate SHA. Carry the exact ledger bytes and hash through
   validation and publication.

The tag command is deliberately candidate-bound:

```sh
candidate_sha=<exact reviewed candidate commit SHA>
git tag -a v0.2.0 "$candidate_sha" -m "Release v0.2.0"
test "$(git cat-file -t refs/tags/v0.2.0)" = tag
test "$(git rev-parse refs/tags/v0.2.0^{})" = "$candidate_sha"
test "$(git cat-file -t "$candidate_sha")" = commit
git push origin refs/tags/v0.2.0
```

Do not tag the trusted-main commit, use a PR head, create a lightweight tag,
or dispatch the publication workflow before the later trusted-main ledger is
present and protected validation has passed.

## Before Tag

1. Merge the approved release-preparation change normally.
2. Sync local `main` with `origin/main`; record that exact trusted-main SHA.
3. Rewrite `release/ledger.json` on trusted main to schema 1, version `0.2.0`,
   and the exact earlier candidate SHA. Do not use the trusted-main SHA as the
   candidate.
4. Run the protected workflow manually with the exact candidate SHA and
   expected version `0.2.0`; require build and all 10 validation cells to pass.
5. Confirm no existing `v0.2.0` tag, PyPI `0.2.0` version, or GitHub Release
   exists. Confirm the `pypi` environment, OIDC Trusted Publisher, tag policy,
   and required reviewers independently.
6. Only after those checks, create and push the annotated tag command above.

## Tag Workflow Checks

- The tag is annotated and peels to the candidate SHA.
- The candidate is a strict ancestor of trusted main and differs from it.
- The ledger is read from trusted main and matches version, candidate SHA, and
  its carried SHA-256 receipt.
- Build and all 10 validation cells pass before publication.
- Publication has only OIDC identity-token permission and uses the `pypi`
  environment.
- Exactly one wheel and one sdist are published from the tag-run artifact;
  publication does not rebuild or use `skip-existing`.

## After PyPI

1. Retain the tag-run receipt, artifact ID, service digest, ledger hash, and
   wheel/sdist hashes.
2. Compare PyPI hashes with the tag-run receipt before accepting publication.
3. Install exact `limitora==0.2.0` wheel and sdist in clean environments.
4. Run the installed API, CLI, Codex fixture, OpenCode loopback, and dependency
   checks without exposing credentials or provider payloads.
5. Create the GitHub Release only after PyPI verification and all smokes pass;
   a GitHub Release does not publish to PyPI.
6. Close issue #52 only after the complete protected publication gate.

## No-Go Gates

- Missing or invalid ledger, wrong trusted-main ledger bytes, or candidate SHA.
- Candidate is not a strict ancestor of trusted main, or equals trusted main.
- Existing `v0.2.0` tag, PyPI `0.2.0` version, or GitHub Release.
- Lightweight tag, PR head, synthetic merge, or unreviewed candidate.
- Failed protected preflight, validation cell, hash, receipt, or installed
  smoke.
- Wrong Pending Trusted Publisher, PyPI environment, tag policy, or workflow
  identity.
- OIDC publication failure or published files differ from the tag-run receipt.
- Published files differ from the tag-run receipt.

## Recovery

Never move or recreate a tag, overwrite files, use `skip-existing`, or silently
retry a partial publication. Stop and record any pre-publication failure. For a
partial publication, evaluate yank and a corrective new version with the
maintainer; never reuse `0.2.0` artifacts under a different source.
