# Limitora 0.2.0 Release Preparation Dossier

**Status:** historical release record. `0.2.0` was published to PyPI, and the
GitHub Release for `v0.2.0` exists. This dossier preserves the protected release
controls and handoff recorded before the annotated tag was pushed.

## Release Scope

- OpenCode Go uses the supported API endpoint through the opt-in provider
  contract and CLI boundary.
- The typed public API, deterministic output projections, provider-aware
  `limitora status` CLI, and Codex JSONL adapter remain covered by tests.
- The base package has no mandatory runtime dependencies; the `opencode-go`
  extra supplies HTTPX.
- Python 3.10-3.14 compatibility and installed wheel/sdist smokes remain
  required.

### Known Limits

- `0.2.0` was published to PyPI, and its GitHub Release exists.
- CI has no real provider credentials or provider access; provider smokes are
  hermetic and network-blocked.
- Issue #18 was closed independently: its protocol/E2E work was not resolved by
  `0.2.0`.
- `python -m limitora` is not a supported entry point.
- No claim is made beyond the evidence recorded after protected validation.

## Release Identity

| Item | Required value |
| --- | --- |
| Version | `0.2.0` |
| Tag | `v0.2.0` |
| Workflow | `.github/workflows/protected-release.yml` |
| Ledger schema | `1` |
| Trusted branch | `origin/main` |
| Candidate relationship | Candidate is a strict ancestor of trusted main |

The ledger is intentionally a preparation anchor, not a claim that the
preparation tree is taggable as `0.2.0`. After PR #53 is merged with the
repository's merge-commit method, the exact two-parent merge commit is `M` and
is the release candidate. Its second parent must be PR #53's reviewed head, so
all reviewed PR commits are included. The ledger must then be rewritten in a
separate, later trusted-main ledger-only commit `T` with `source_sha` set to
`M`. Do not substitute the preparation head, a PR head, or a newly edited SHA.

This two-commit boundary is required because a candidate cannot contain a
ledger that authorizes the candidate's own SHA without self-reference.

## Required Merge Boundary

Merge PR #53 into the current trusted `main` with `--no-ff`; the resulting
two-parent commit is `M`. Do not squash, rebase, or use a synthetic merge. Run
this block in Bash and stop if any command fails:

```sh
set -euo pipefail
test "$(gh pr view 53 --json state --jq '.state')" = OPEN
git fetch origin main
git switch main
git pull --ff-only origin main
base_sha=$(git rev-parse HEAD)
test "$base_sha" = "$(git rev-parse origin/main^{commit})"
pr_head_sha=$(gh pr view 53 --json headRefOid --jq '.headRefOid')
git fetch origin pull/53/head
test "$(git rev-parse FETCH_HEAD)" = "$pr_head_sha"
test "$(git cat-file -t "$pr_head_sha")" = commit
git merge --no-ff "$pr_head_sha" -m "Merge pull request #53"
merge_sha=$(git rev-parse HEAD)
test "$merge_sha" != "$pr_head_sha"
test "$(git cat-file -t "$merge_sha")" = commit
test "$(git rev-parse "$merge_sha^{commit}")" = "$merge_sha"
parents=($(git show -s --format=%P "$merge_sha"))
test "${#parents[@]}" -eq 2
test "${parents[0]}" = "$base_sha"
test "${parents[1]}" = "$pr_head_sha"
git merge-base --is-ancestor "$pr_head_sha" "$merge_sha"
git show "$merge_sha:pyproject.toml" | grep -Fx 'version = "0.2.0"'
candidate_sha="$merge_sha"
```

Rewrite `release/ledger.json` only in a separate, later `main` commit `T`. That
commit must directly follow `M` and change no other path. After that
authorization commit is pushed, resolve and verify the trusted main SHA before
any tag or protected publication dispatch:

```sh
set -euo pipefail
: "${MERGE_SHA:?set MERGE_SHA to the exact verified two-parent merge commit SHA}"
merge_sha="$MERGE_SHA"
test "$(git cat-file -t "$merge_sha")" = commit
test "$(git rev-parse "$merge_sha^{commit}")" = "$merge_sha"
git fetch origin main
trusted_main_sha=$(git rev-parse origin/main^{commit})
test "$trusted_main_sha" != "$merge_sha"
git merge-base --is-ancestor "$merge_sha" "$trusted_main_sha"
test "$(git rev-parse "$trusted_main_sha^")" = "$merge_sha"
test "$(git diff-tree --no-commit-id --name-only -r "$trusted_main_sha")" = "release/ledger.json"
test "$(git rev-parse "$merge_sha:release/ledger.json")" != "$(git rev-parse "$trusted_main_sha:release/ledger.json")"
git show "$trusted_main_sha:release/ledger.json" | python -c 'import json, sys; d=json.load(sys.stdin); assert d == {"schema_version": 1, "version": "0.2.0", "source_sha": sys.argv[1]}' "$merge_sha"
candidate_sha="$merge_sha"
```

The final command is fail-closed: it succeeds only when the trusted-main
ledger has exactly the schema, version, and `M` source SHA required by this
dossier. The parent and changed-path checks prove that `T` is the later
ledger-only authorization commit. Do not tag or authorize publication if either
block fails.

## Candidate and Ledger Strategy

The existing workflow is intentionally unchanged. It avoids the
self-referential candidate SHA as follows:

1. On a tag push, fetch `origin/main` and resolve `trusted_main_sha` from
   `origin/main^{commit}`.
2. Peel the annotated `v0.2.0` tag to `candidate_sha` (the previously verified
   `M`); require the tag to be annotated, the candidate to be a commit, and the
   candidate to differ from `trusted_main_sha`.
3. Require the candidate to be an ancestor of `trusted_main_sha`, then check
   out the candidate itself for version inspection, build, and validation.
4. Read the ledger from trusted main (`T`) with
   `git show "$trusted_main_sha:release/ledger.json"`, not from the tagged
   tree.
5. Require schema 1, version `0.2.0`, and the ledger source SHA to equal `M`,
   the peeled candidate SHA. Carry the exact ledger bytes and hash through
   validation and publication.

The tag command is deliberately candidate-bound:

```sh
: "${MERGE_SHA:?set MERGE_SHA to the exact verified two-parent merge commit SHA}"
candidate_sha="$MERGE_SHA"
git tag -a v0.2.0 "$candidate_sha" -m "Release v0.2.0"
test "$(git cat-file -t refs/tags/v0.2.0)" = tag
test "$(git rev-parse refs/tags/v0.2.0^{})" = "$candidate_sha"
test "$(git cat-file -t "$candidate_sha")" = commit
git push origin refs/tags/v0.2.0
```

Do not tag the trusted-main commit, use a PR head, create a lightweight tag,
or dispatch the publication workflow before the later trusted-main ledger is
present and protected validation has passed.

## Before Tag

1. Complete the Required Merge Boundary after PR #53 is merged and retain the
   exact two-parent merge commit `M` selected from GitHub's merge commit.
2. Sync local `main` with `origin/main`; record the later trusted-main SHA only
   after the ledger authorization commit exists.
3. Rewrite `release/ledger.json` on trusted main to schema 1, version `0.2.0`,
   and `source_sha` equal to `M`. Do not use the trusted-main SHA or PR head as
   the candidate.
4. Verify `M` is a strict ancestor of `T`, `M != T`, `T` directly follows `M`
   and changes only `release/ledger.json`, and `M` has exactly two parents with
   PR #53's head as its second parent. Do not proceed after a squash, rebase,
   or synthetic merge.
5. Run the protected workflow manually with the exact candidate SHA and
   expected version `0.2.0`; require build and all 10 validation cells to pass.
6. Confirm no existing `v0.2.0` tag, PyPI `0.2.0` version, or GitHub Release
   exists. Confirm the `pypi` environment, OIDC Trusted Publisher, tag policy,
   and required reviewers independently.
7. Only after those checks, create and push the annotated tag command above.

## Tag Workflow Checks

- The tag is annotated and peels to the candidate SHA.
- `M` is a strict ancestor of trusted main (`T`) and differs from it; `M` has
  exactly two parents and its second parent is PR #53's reviewed head.
- `T` directly follows `M` and changes only `release/ledger.json`.
- The ledger is read from `T` and matches version, `M`, and its carried SHA-256
  receipt.
- Build and all 10 validation cells pass before publication.
- Publication has only OIDC identity-token permission and uses the `pypi`
  environment.
- Exactly one wheel and one sdist are published from the tag-run artifact;
  publication does not rebuild or use `skip-existing`.

## After PyPI

1. Retain the tag-run receipt, artifact ID, service digest, ledger hash, and
   wheel/sdist hashes.
2. Compare PyPI hashes with the tag-run receipt before accepting publication.
3. Install exact `limitora==0.2.0` wheel and sdist in clean environments.
4. Run the installed API, CLI, Codex fixture, OpenCode loopback, and dependency
   checks without exposing credentials or provider payloads.
5. Create the GitHub Release only after PyPI verification and all smokes pass;
   a GitHub Release does not publish to PyPI.
6. Close issue #52 only after the complete protected publication gate.

## No-Go Gates

- Missing or invalid ledger, wrong trusted-main ledger bytes, or candidate SHA.
- Candidate is not a strict ancestor of trusted main, or equals trusted main.
- Existing `v0.2.0` tag, PyPI `0.2.0` version, or GitHub Release.
- Lightweight tag, PR head, synthetic merge, or unreviewed candidate.
- Failed protected preflight, validation cell, hash, receipt, or installed
  smoke.
- Wrong Pending Trusted Publisher, PyPI environment, tag policy, or workflow
  identity.
- OIDC publication failure or published files differ from the tag-run receipt.
- Published files differ from the tag-run receipt.

## Recovery

Never move or recreate a tag, overwrite files, use `skip-existing`, or silently
retry a partial publication. Stop and record any pre-publication failure. For a
partial publication, evaluate yank and a corrective new version with the
maintainer; never reuse `0.2.0` artifacts under a different source.
