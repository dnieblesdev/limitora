# Limitora 0.3.0 Release Preparation Dossier

**Status:** release preparation only. `0.3.0` is not published to PyPI, and a
GitHub Release does not yet exist. This dossier defines the candidate, the
ledger authorization handoff, and the protected publication runbook.

## Quick Path

1. Merge the approved preparation PR with a true two-parent merge commit `M`.
2. Merge a separate PR that changes only `release/ledger.json`; its trusted
   main commit is `T` and authorizes `source_sha = M`.
3. Run the protected workflow manually with candidate `M` and expected version
   `0.3.0`; publication must be skipped and all validation cells must pass.
4. Create and push the annotated `v0.3.0` tag at `M`, never at `T`.
5. Compare the published PyPI hashes with the tag-run receipt, install both
   exact distributions in clean environments, and create the GitHub Release.

Merging this preparation work unit or its later ledger-only authorization does
not itself authorize a tag, publication, or GitHub Release. Issue #57 tracks
the approved preparation work unit; it is not a publication approval.

## Release Identity

| Item | Required value |
| --- | --- |
| Version | `0.3.0` |
| Tag | `v0.3.0` |
| Workflow | `.github/workflows/protected-release.yml` |
| Ledger schema | `1` |
| Trusted branch | `origin/main` |
| Candidate | Exact reviewed merge commit `M` |
| Authorization | Later ledger-only trusted-main commit `T` |

The ledger on this preparation branch is an explicit temporary anchor at the
clean base. It is not final authorization and must not be used as a tag
decision. After the preparation PR is merged, the exact reviewed merge commit
is `M`. A separate later ledger-only commit `T` must set the ledger source to
`M`. This two-commit boundary avoids a self-referential candidate ledger.

## Candidate Merge Boundary

Before the approved preparation PR is merged, capture the exact trusted main
base in a file outside the repository. Do not recalculate this value after
main advances to `M`:

```bash
set -euo pipefail
BASE_SHA_FILE="${BASE_SHA_FILE:-/tmp/limitora-0.3.0-base-sha}"
git fetch origin main
base_sha="$(git rev-parse origin/main^{commit})"
test "$(git rev-parse origin/main^{commit})" = "$base_sha"
printf '%s\n' "$base_sha" > "$BASE_SHA_FILE"
```

After the approved preparation PR is merged, resolve its actual GitHub merge
commit and verify that its first parent is the captured trusted-main base and
its second parent is the reviewed PR head. Do not squash, rebase, or use a
synthetic merge. Stop if any command fails:

```bash
set -euo pipefail
BASE_SHA_FILE="${BASE_SHA_FILE:-/tmp/limitora-0.3.0-base-sha}"
: "${PREPARATION_PR:?set PREPARATION_PR to the approved preparation PR number}"
test -s "$BASE_SHA_FILE"
base_sha="$(cat "$BASE_SHA_FILE")"
[[ "$base_sha" =~ ^[0-9a-f]{40}$ ]]
test "$(git cat-file -t "$base_sha")" = commit
test "$(gh pr view "$PREPARATION_PR" --json state --jq '.state')" = MERGED
pr_head_sha="$(gh pr view "$PREPARATION_PR" --json headRefOid --jq '.headRefOid')"
merge_sha="$(gh pr view "$PREPARATION_PR" --json mergeCommit --jq '.mergeCommit.oid')"
git fetch origin main
git fetch origin "pull/$PREPARATION_PR/head"
test "$(git rev-parse FETCH_HEAD)" = "$pr_head_sha"
test "$(git cat-file -t "$pr_head_sha")" = commit
test "$(git cat-file -t "$merge_sha")" = commit
test "$(git rev-parse "$merge_sha^{commit}")" = "$merge_sha"
parents=($(git show -s --format=%P "$merge_sha"))
test "${#parents[@]}" -eq 2
test "${parents[0]}" = "$base_sha"
test "${parents[1]}" = "$pr_head_sha"
git merge-base --is-ancestor "$pr_head_sha" "$merge_sha"
git show "$merge_sha:pyproject.toml" | grep -Fx 'version = "0.3.0"'
candidate_sha="$merge_sha"
```

The verified `candidate_sha` is `M`. Do not substitute the preparation branch
head, the PR head, the trusted-main commit, or a newly edited SHA.

## Ledger Authorization Boundary

The ledger authorization must be a separate later main commit `T` that directly
follows `M` and changes no path other than `release/ledger.json`:

```sh
set -euo pipefail
: "${MERGE_SHA:?set MERGE_SHA to the exact verified two-parent merge commit SHA}"
merge_sha="$MERGE_SHA"
test "$(git cat-file -t "$merge_sha")" = commit
test "$(git rev-parse "$merge_sha^{commit}")" = "$merge_sha"
git fetch origin main
trusted_main_sha="$(git rev-parse origin/main^{commit})"
test "$trusted_main_sha" != "$merge_sha"
git merge-base --is-ancestor "$merge_sha" "$trusted_main_sha"
test "$(git rev-parse "$trusted_main_sha^")" = "$merge_sha"
test "$(git diff-tree --no-commit-id --name-only -r "$trusted_main_sha")" = "release/ledger.json"
test "$(git rev-parse "$merge_sha:release/ledger.json")" != "$(git rev-parse "$trusted_main_sha:release/ledger.json")"
git show "$trusted_main_sha:release/ledger.json" | python -c 'import json, sys; d=json.load(sys.stdin); assert d == {"schema_version": 1, "version": "0.3.0", "source_sha": sys.argv[1]}' "$merge_sha"
candidate_sha="$merge_sha"
```

The final assertion is fail-closed: `T` must authorize exactly version
`0.3.0` and candidate `M`. Do not tag or publish if the parent, changed-path,
ledger, or ancestry checks fail.

## Protected Preflight

Run the protected workflow manually from trusted main before creating a tag:

```sh
gh workflow run protected-release.yml --ref main \
  -f candidate-sha="$MERGE_SHA" -f expected-version=0.3.0
gh run watch <preflight-run-id> --exit-status
```

The `workflow_dispatch` path builds and validates the exact candidate but skips
the publish job. Require the build and all 10 Linux/Windows Python 3.10-3.14
validation cells to pass. Retain the run URL, artifact ID, service digest,
receipt, manifest, wheel hash, sdist hash, and inventory hash.

The protected workflow is intentionally unchanged. It checks out `M`, builds
one wheel and one sdist, carries the exact artifact bundle through validation,
and never rebuilds during publication. The publish job is gated to an
annotated `v0.3.0` tag, successful validation, the `pypi` environment, and
OIDC identity-token permission. It does not use `skip-existing`.

## Annotated Tag

Only after `T` exists and the protected preflight passes, create the immutable
candidate-bound tag:

```sh
: "${MERGE_SHA:?set MERGE_SHA to the exact verified two-parent merge commit SHA}"
candidate_sha="$MERGE_SHA"
git tag -a v0.3.0 "$candidate_sha" -m "Release v0.3.0"
test "$(git cat-file -t refs/tags/v0.3.0)" = tag
test "$(git rev-parse refs/tags/v0.3.0^{})" = "$candidate_sha"
test "$(git cat-file -t "$candidate_sha")" = commit
git push origin refs/tags/v0.3.0
```

The tag must peel to `M`, not `T` or the PR head. Do not push directly to
`main`, move or recreate a tag, or dispatch publication before this boundary.
The tag workflow reads the authorization ledger from trusted main with
`git show "$trusted_main_sha:release/ledger.json"`, not from the tagged tree.

## PyPI Verification and GitHub Release

After the protected tag workflow publishes through the OIDC Trusted Publisher:

1. Retain the tag-run artifact receipt, artifact service digest, ledger hash,
   manifest hash, wheel hash, and sdist hash.
2. Compare the exact PyPI wheel and sdist SHA-256 hashes with the tag-run
   receipt. Published files must be the validated tag-run artifacts.
3. Install exact `limitora==0.3.0` wheel and sdist in separate clean
   environments, run the installed API and CLI smoke checks, and run
   `python -m pip check`.
4. Verify the optional `opencode-go` dependency path without exposing
   credentials or private provider payloads.
5. Create the GitHub Release only after PyPI hash and install verification:
   `gh release create v0.3.0 --verify-tag --title "Limitora 0.3.0"`.

A GitHub Release does not publish to PyPI. If any hash, receipt, install, or
smoke check differs, stop before creating the GitHub Release.

## No-Go Gates

- Missing or invalid ledger, wrong trusted-main ledger bytes, or wrong source
  SHA for `M`.
- Candidate is not a strict ancestor of trusted main, equals `T`, or is not the
  exact reviewed two-parent merge.
- Existing `v0.3.0` tag, PyPI `0.3.0` version, or GitHub Release.
- Lightweight tag, PR head, direct main push, squash, rebase, or synthetic
  merge.
- Failed protected preflight, validation cell, artifact service digest, hash,
  receipt, manifest, or installed smoke.
- Wrong Pending Trusted Publisher, PyPI environment, tag policy, or workflow
  identity.
- OIDC publication failure or published files differ from the tag-run receipt.
- Rebuild during publication, `skip-existing`, or an unverified artifact.

## Rollback and Recovery

Before publication, stop and record the failed gate; remove only the
uncommitted preparation changes or the release-preparation branch if the work
unit must be abandoned. Never move or recreate a tag, overwrite a published
file, use `skip-existing`, or silently retry a partial publication.

After a partial publication, do not reuse `0.3.0` artifacts under another
source. Preserve all receipts, evaluate yank and a corrective new version with
the maintainer, and create no GitHub Release until the corrective publication
has been independently verified.
