# Limitora 0.1.0 Final Gate Dossier

**Status:** historical release record. `0.1.0` was published to PyPI, and the
GitHub Release for `v0.1.0` exists. This document preserves the pre-publication
evidence and controls recorded at release time; it is not a current publication
approval.

## Release Notes (Historical)

- Typed public API, including `py.typed`.
- Tested on Python 3.10-3.14 on Linux and Windows.
- The base package has no mandatory runtime dependencies; the `opencode-go`
  extra supplies HTTPX.
- Installed `limitora status` CLI and Codex/OpenCode Go provider adapters.
- Audited wheel and sdist with clean artifact installation and execution.

### Known Limits

- The approved protected-release run below skipped publication; that is
  historical pre-publication evidence, not the current publication status.
- CI has no real provider credentials or provider access; provider smokes are
  hermetic and network-blocked.
- Issue #18 remains open and independent: its protocol/E2E work is not resolved by `0.1.0`.
- `python -m limitora` is not a supported entry point.
- No claim is made beyond the evidence recorded below.

## Go/No-Go Runbook

### Before Tag: Steps 1-10

1. Merge approved PR4 normally; do not tag its merge commit.
2. Sync local `main` with `origin/main` after the merge.
3. Set `trusted_main_sha` to the real PR4 merge commit SHA, never a PR head or
   synthetic merge.
4. Freeze `main` at that SHA and prohibit unrelated changes.
5. Read `release/ledger.json` from `origin/main`; it must authorize version
   `0.1.0` and the exact candidate source SHA.
6. Verify the ledger has schema 1, exactly the approved version, and the
   approved 40-character lowercase source SHA.
7. Verify the candidate exists and is an ancestor of `trusted_main_sha`.
8. Verify the candidate SHA is different from the PR4 merge SHA.
9. Reconfirm both rulesets, the `pypi` environment, tag policy, OIDC, and the
   registered Pending Trusted Publisher.
10. At the time of this pre-publication gate, confirm no `v0.1.0` tag, GitHub
    Release, or PyPI `0.1.0` exists; keep #33 and #18 open at this gate.

### Tag Commands

The annotated tag targets the candidate SHA, never `trusted_main_sha` or the
PR4 merge. Push only the tag ref; never move, recreate, or replace it.

```sh
candidate_sha=678c095c55a8ddfec344d96c1872c3f75340f9a8
git tag -a v0.1.0 "$candidate_sha" -m "Release v0.1.0"
test "$(git cat-file -t refs/tags/v0.1.0)" = tag
test "$(git rev-parse refs/tags/v0.1.0^{})" = "$candidate_sha"
test "$(git cat-file -t "$candidate_sha")" = commit
git push origin refs/tags/v0.1.0
```

### Tag Workflow Checks

- Check the tag is annotated and its peeled commit is the candidate.
- Check the tag commit and candidate are distinct from the trusted main PR4
  merge, and the ledger is read from trusted main.
- Check ledger version/source and ledger SHA against the trusted-main SHA.
- Require the build and all 10 validation cells to pass before publish.
- Require the `pypi` environment and OIDC only for publication.
- Require exactly one artifact and service digest, one wheel, and one sdist.
- Publish the downloaded tag-run artifact only: no checkout or rebuild in
  publish, and no `skip-existing`.

### After PyPI: Steps 1-11

1. Retain the tag-run receipt, artifact ID, and service digest.
2. Compare the PyPI wheel and sdist hashes with the tag-run receipt before
   accepting publication.
3. Create a clean virtual environment and install the exact wheel:

   ```sh
   python -m venv .release-venv
   .release-venv/bin/python -m pip install --no-deps limitora==0.1.0
   ```

4. Run the installed CLI and API smoke:

   ```sh
   .release-venv/bin/limitora status
   .release-venv/bin/python -c "import limitora; print(limitora.__all__)"
   ```

5. Create another clean environment and install the exact sdist with its
   build requirements.
6. Repeat the CLI and typed public API smoke against that sdist installation.
7. Install the optional extra and check dependencies:

   ```sh
   .release-venv/bin/python -m pip install "limitora[opencode-go]==0.1.0"
   .release-venv/bin/python -m pip check
   ```

8. Confirm the `opencode-go` extra installs HTTPX and that the base install
   did not require it.
9. Confirm the published files, receipt hashes, and one-wheel/one-sdist
   shape still match the tag-run artifact.
10. Create the GitHub Release only after PyPI verification and all smokes
    complete; never use it to publish files.
11. Close #33 only after the complete gate; keep #18 open as independent
    protocol/E2E work.

## No-Go Gates

- Missing or invalid ledger.
- Wrong ledger or candidate source SHA.
- Main state does not match the trusted merge state.
- Candidate is not an ancestor of trusted main.
- Existing `v0.1.0` tag.
- Tag is lightweight instead of annotated.
- Tag points to the PR4 merge.
- Existing PyPI `0.1.0` version.
- Existing GitHub Release for `v0.1.0`.
- Inactive main or tag ruleset.
- Wrong PyPI environment.
- Tag policy is not `v*`.
- Wrong Pending Trusted Publisher.
- Wrong workflow identity.
- Manual gate evidence cannot be verified.
- PR4 validation/CI fails.
- Hashes or receipts are inconsistent.
- Partial publication.
- OIDC publication failure.
- Published files differ from the tag-run receipt.

## Recovery

Never use `skip-existing`, overwrite files, move/recreate a tag, or hide a
partial publication. Stop and record any pre-publication failure. For a
partial publication, evaluate yank and a corrective version rather than
silently retrying. Post-`0.1.0` fixes use a new version, for example `0.1.1`.
